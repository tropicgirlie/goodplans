# Good Plans — UI, UX and functionality audit

Reviewed 9 October 2026. Scope: current local source and UI, isolated development backend, automated tests, and read-only production checks. No application fixes or production changes were made during this audit. Existing uncommitted work remains intact.

Implementation follow-up: this is the pre-fix audit snapshot. See [BACKLOG.md](./BACKLOG.md) for current completion and release status.

## Verdict

**Not ready for broad public launch.** The hosting backend has strong automated coverage, but the current interface has significant broken handoffs, accessibility gaps and privacy inconsistencies. Resolve the P1 findings, deploy the intended version, and complete a real-domain guest/newsletter smoke test before opening a small creator-led pilot.

Public personal planning is possible without an account in the current local version. Publishing invitations remains restricted to approved hosts; this is not public self-service organiser registration.

## Design verdict and health score

**Anti-pattern verdict: pass.** The warm cream, coral and purple palette, cut-paper artwork and expressive typography give the site a distinct identity. Keep that design. The problems are density, inconsistent interactions and overly tight type, rather than a need to replace the visual direction.

## P1 — fix before release

### 1. Dashboard logout does nothing

- **Location:** [App.jsx:1766](/Users/Dublin-Osx/code/meetfriendsplanner/src/App.jsx:1766), [SettingsPanel.jsx:210](/Users/Dublin-Osx/code/meetfriendsplanner/src/components/SettingsPanel.jsx:210).
- **Category:** Functionality / UX.
- **Evidence:** The dashboard renders SettingsPanel without `onLogout`, while its logout button calls that prop. Clicking it in the signed-in local session leaves the user signed in.
- **Impact:** A host cannot end their session from the settings screen, especially problematic on a shared device. The homepage has a separate working logout path.
- **Recommendation:** Pass the existing logout handler into the dashboard settings and visibly confirm the signed-out state. Verify session invalidation, not just the label change.
- **Suggested command:** `$impeccable harden`.

### 2. Planning settings lacks modal keyboard behaviour

- **Location:** [SettingsPanel.jsx:144](/Users/Dublin-Osx/code/meetfriendsplanner/src/components/SettingsPanel.jsx:144).
- **Category:** Accessibility.
- **Evidence:** A div declares `role="dialog"` and `aria-modal="true"`, but there is no initial focus, focus containment/restoration, background inertness or Escape handling. In the browser, opening it leaves focus on the underlying Planning settings button; Escape does not dismiss it.
- **Impact:** Keyboard and assistive-technology users can interact with the obscured page and lose their place.
- **Standard:** Modal dialog interaction expectations; relevant to meaningful focus order (WCAG 2.4.3).
- **Recommendation:** Reuse the application's native dialog pattern, set initial focus, contain focus, support Escape and restore focus to the opener.
- **Suggested command:** `$impeccable harden`.

### 3. Homepage planning actions discard the user's choices

- **Location:** [OriginalHome.jsx:201](/Users/Dublin-Osx/code/meetfriendsplanner/src/components/OriginalHome.jsx:201), [OriginalHome.jsx:474](/Users/Dublin-Osx/code/meetfriendsplanner/src/components/OriginalHome.jsx:474).
- **Category:** Functionality / UX.
- **Evidence:** Find a good idea only opens My people. The entered name, activity and moment are not carried into the dashboard or a draft. The example recommendation's Make a plan action similarly ignores the chosen idea.
- **Impact:** Visitors fill in a form and lose the context they expect to continue with. The example disclosure does not explain this dead-end handoff.
- **Recommendation:** Carry the selected activity/context into an editable local draft. Either preserve typed names for explicit review or remove the unused input and clearly name the action Open my planner.
- **Suggested command:** `$impeccable clarify`.

### 4. Recommendations do not use personal preferences, and map labels can be wrong

- **Location:** [AffinityMatchMatrix.jsx:44](/Users/Dublin-Osx/code/meetfriendsplanner/src/components/AffinityMatchMatrix.jsx:44), [worker/src/index.js:421](/Users/Dublin-Osx/code/meetfriendsplanner/worker/src/index.js:421), [GoogleMapsExplorer.jsx:60](/Users/Dublin-Osx/code/meetfriendsplanner/src/components/GoogleMapsExplorer.jsx:60).
- **Category:** Functionality / UX / trust.
- **Evidence:** Personal requests send anonymous names only, with no interests, noise preferences or selected city. The backend defaults unknown ages to 30 and scores missing personality/energy data as the social/noisy branch. It ignores the map's activity filter; the frontend then applies the requested activity as the venue label. A pottery studio, tapas venue and board-game café appeared as contemporary art galleries in the browser. The backend's 60s branch is also unreachable because the 50+ branch comes first.
- **Impact:** The promise of ideas suited to the actual people is unsupported, and inaccurate venue labels mislead planning.
- **Recommendation:** Keep names and notes private. Use explicit, optional non-identifying activity/accessibility preferences, preferably scored locally. Treat unknown values neutrally, pass the chosen city, filter by actual category and retain each venue's true label. Avoid age/personality assumptions as substitutes for stated needs.
- **Suggested command:** `$impeccable harden`.

### 5. Automatic third-party requests are missing from the privacy explanation

- **Location:** [GoogleMapsExplorer.jsx:130](/Users/Dublin-Osx/code/meetfriendsplanner/src/components/GoogleMapsExplorer.jsx:130), [index.css:1](/Users/Dublin-Osx/code/meetfriendsplanner/src/index.css:1), [mockData.js:7](/Users/Dublin-Osx/code/meetfriendsplanner/src/data/mockData.js:7), [ServicePages.jsx:25](/Users/Dublin-Osx/code/meetfriendsplanner/src/components/ServicePages.jsx:25).
- **Category:** Privacy / UX.
- **Evidence:** Google Fonts loads from an external stylesheet; fictional friend avatars load from Unsplash; the Google Maps iframe loads as it enters view. The privacy page describes opening external map links, but not automatic embedded requests or these additional providers.
- **Impact:** Device-local friend storage does not mean a visitor makes no third-party requests. The current explanation understates that distinction.
- **Recommendation:** Self-host fonts and example avatars, make the map click-to-load, and describe remaining external requests accurately. This is a verified implementation/disclosure mismatch, not a legal compliance certification.
- **Suggested command:** `$impeccable harden` and `$impeccable clarify`.

### 6. Small text has insufficient contrast

- **Location:** [index.css:4](/Users/Dublin-Osx/code/meetfriendsplanner/src/index.css:4), [index.css:12](/Users/Dublin-Osx/code/meetfriendsplanner/src/index.css:12), [index.css:13](/Users/Dublin-Osx/code/meetfriendsplanner/src/index.css:13).
- **Category:** Accessibility / theming.
- **Evidence:** Rendered homepage colours: white on coral `#e94f38` is about **3.72:1** for 13px buttons; coral on cream `#fff0ca` is **3.29:1** for 11px labels; blue `#2e6edf` on cream is **4.21:1** for small text.
- **Impact:** Important labels/actions are harder to read for people with low vision and in bright conditions.
- **Standard:** These normal-size text combinations fall below WCAG 1.4.3's 4.5:1 threshold.
- **Recommendation:** Introduce accessible text/action colour tokens while retaining the decorative palette. Check all hover, disabled, focus and selected states after changing tokens.
- **Suggested command:** `$impeccable colorize`.

### 7. Optional sync consent is browser-wide, not tied to the account

- **Location:** [App.jsx:831](/Users/Dublin-Osx/code/meetfriendsplanner/src/App.jsx:831), [useCloudWorkspace.js:43](/Users/Dublin-Osx/code/meetfriendsplanner/src/lib/useCloudWorkspace.js:43).
- **Category:** Privacy / functionality.
- **Evidence:** `good-plans-sync-enabled` is a global persisted boolean. Account changes do not reset it. A later account can start syncing because a previous account enabled it. The workspace hook has ownership safeguards and backups, but those do not establish the new account's opt-in.
- **Impact:** On a shared browser, sign-in can trigger unexpected server access and replace the visible local workspace with a remote workspace. This path is code-verified, not manually reproduced with two accounts during this audit.
- **Recommendation:** Scope consent to the authenticated account, suspend sync on account changes, and clearly preview merge/replace behaviour before activation. Preserve the existing owner checks and backups.
- **Suggested command:** `$impeccable harden`.

### 8. Organiser defaults are not carried into a new series

- **Location:** [App.jsx:239](/Users/Dublin-Osx/code/meetfriendsplanner/src/App.jsx:239), [App.jsx:1766](/Users/Dublin-Osx/code/meetfriendsplanner/src/App.jsx:1766).

### 9. Unrelated dashboard changes reload recommendations

- **Location:** [App.jsx:1765](/Users/Dublin-Osx/code/meetfriendsplanner/src/App.jsx:1765), [AffinityMatchMatrix.jsx:34](/Users/Dublin-Osx/code/meetfriendsplanner/src/components/AffinityMatchMatrix.jsx:34).

- **Evidence/impact:** A new filtered selection array is passed on every render, and the effect depends on that array. Opening settings recreates suggestion controls; unrelated changes reset results and expanded state, producing extra requests and potential flicker.
- **Recommendation:** Depend on stable selection IDs and stable friend data; only reset expanded/loading state when the actual inputs change.
- **Suggested command:** `$impeccable optimize`.

### 10. Two friend editors use incompatible data models

- **Location:** [SettingsPanel.jsx:112](/Users/Dublin-Osx/code/meetfriendsplanner/src/components/SettingsPanel.jsx:112), [App.jsx:1902](/Users/Dublin-Osx/code/meetfriendsplanner/src/App.jsx:1902).

- **Evidence/impact:** Settings saves `likes`/`avoids`, while My people saves `note` and replaces the whole object. Editing a settings-created friend in My people can discard structured details. Duplicate-name validation exists only in My people. A note-created friend appears without Likes/Avoids in settings.

### 13. Several touch targets are too short

- **Location:** [App.jsx:1315](/Users/Dublin-Osx/code/meetfriendsplanner/src/App.jsx:1315), [App.jsx:1832](/Users/Dublin-Osx/code/meetfriendsplanner/src/App.jsx:1832), [index.css:17](/Users/Dublin-Osx/code/meetfriendsplanner/src/index.css:17).
- **Category:** Responsive design / accessibility.
- **Evidence/impact:** Measured heights include about 20px for sync, 18px for footer Host sign-in, 21px for privacy links and 18–20px for event/series links. Small targets are harder to use with fingers or limited motor precision.
- **Standard:** Recommend 44px hit areas. WCAG 2.5.8 has size/spacing exceptions; this audit does not claim every small link violates it.
- **Recommendation:** Add invisible hit-area padding/minimum sizes without making the visual design bulky.
- **Suggested command:** `$impeccable adapt`.

### 14. Large artwork dominates loading cost

- **Location:** `public/images/good-plans-hero-sticker.png`, `good-plans-invite-collage.png`, and the Good Plans mark/favicon.
- **Category:** Performance.
- **Evidence/impact:** Hero and invitation artwork are approximately 3.3 MB and 3.4 MB; the mark/favicon is around 1.1 MB. Several images load eagerly. These assets can cost far more than the roughly 100 KB gzip JS bundle on mobile connections. Actual loading times were not measured.
- **Recommendation:** Preserve the artwork; export appropriately sized WebP/AVIF versions, use responsive sources, a small favicon and lazy loading below the fold.
- **Suggested command:** `$impeccable optimize`.

## Systemic patterns

The main gaps occur at UI-to-model boundaries: form choices are not carried through, friend editors disagree, and preferences are disconnected from recommendations and draft defaults. Backend tests pass because they exercise the API directly. Add a small set of meaningful browser journeys covering these handoffs, settings logout and keyboard interaction.

The privacy model is moving in the right direction but needs consistent account-scoped consent, provider disclosure and state-aware copy. Colour and spacing fixes should be made through shared tokens rather than scattered overrides.

## What is working well

- The original visual identity is preserved; the example circle is clearly labelled and no longer relies on fake compatibility percentages.
- Current local personal planning works without login. Friends and drafts persist on the device after reload; the recommendation request does not send actual personal names or notes.
- Main draft modals use native dialog behaviour; forms generally have labels and friend selection exposes pressed states.
- Undated drafts correctly appear under Still planning; calendar navigation and saved-idea recovery controls work.
- Backend tests cover private invitation access, one-use authentication, recurrence, capacity/plus-ones, waitlist promotion, revision conflicts and cancellation.
- Newsletter signup has separate consent/confirmation; candidates and editions require organiser review before public listing or sending.
- Invalid invitation and subscription links have clear recovery states. Privacy/support pages fit the inspected phone viewport.

## Production requirements before a pilot

1. Resolve P1 issues and deploy the intended local-first version. The current source modifications are uncommitted, and this audit did not deploy them. Do not assume the live site has the same privacy behaviour as the local build.
2. Choose a discovery launch scope. Production `/api/discovery` returned `{"events":[]}` and `TICKETMASTER_API_KEY` was absent. Use reviewed manual events for a pilot, or configure an authorised source. Independent classes/retreats still need local sources or manual curation; no source establishes safety, accessibility or current availability by itself.
3. Verify email delivery outcomes. `RESEND_API_KEY` and `EMAIL_FROM` are configured, and the user previously confirmed receiving a sign-in code. `RESEND_WEBHOOK_SECRET` was absent during this audit; complete webhook setup and verify actual delivery/bounce callbacks.
4. Run the real-domain flow with designated test recipients: host login → single event and series → private invitation → RSVP/plus-one/waitlist → edit/cancel notice. Include the guest phone UI and calendar export.
5. Run a deliberately approved test newsletter: subscribe/confirm → reviewed edition → delivery → add to plan → unsubscribe/deletion. Do not treat local provider mocks as evidence of live sending.
6. Recheck explicit opt-in sync in a second browser and account switching on a shared browser, including conflict/recovery behaviour.
7. Confirm operator/contact, retention and deletion handling; assign support/operations ownership; verify external failure alerts and a database restore drill. These older backlog items were not established as complete here.
8. Keep the host pilot allowlisted, or implement and test public organiser registration before advertising it. Shared date voting, bulk edits across future series occurrences and two-way calendar sync remain follow-ups rather than pilot requirements.

This audit is not a penetration test, legal review, real deliverability audit, load test or exhaustive device/assistive-technology certification.
