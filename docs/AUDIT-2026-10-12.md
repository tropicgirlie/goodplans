# Good Plans: UI, UX and user-flow audit

12 October 2026. Reviewed source commit `ffe0ec1`, a fresh production build served by an isolated local Worker/D1 database, and read-only production pages at https://goodplans.luana.systems/.

## Verdict

The core friend-to-event flow works in the current source, but the website is not ready for a broad public launch. The live site still serves an older version, and this pass found 13 additional implementation/usability issues: four P1 and nine P2. No P0 was reproduced in the standard single-invitation journey. The shared-browser invitation edge case must be fixed before release.

This is a review, not an implementation pass. GP-18–GP-30 are open in [the backlog](./BACKLOG.md). Previously checked GP-01–GP-17 describe the earlier local implementation; they do not establish that production has those fixes.

## Detailed findings

### [P1] GP-18: Published-event management handoff is stale

**Location:** `src/App.jsx:1067`, `src/App.jsx:1883`, `src/components/HostPortal.jsx:26` and `:35`.

**Reproduction:** Start publishing while signed out. After OTP, the portal is already mounted behind the retained draft. Publish successfully, then choose Manage event & guests. The list contains the seed event but not the newly published outing. Manual Refresh reveals it.

**Impact:** A host thinks publishing failed or manages the wrong event. Even when navigation remounts the portal, it lands on the list rather than the requested event.

**Recommendation:** Pass the intended remote event ID into the portal; refresh/invalidate host data on publication and select that event. Preserve selection in its URL. Add a meaningful UI regression for publish → manage.

**Category / suggested command:** Functionality, UX / `$impeccable harden`.

### [P1] GP-19: Hosted events and series are not fully represented in My plans

**Location:** `src/App.jsx:905`, `:945`, `:1100`.

**Reproduction:** Publish a three-week series. Portal lists all three dates; personal plans/calendar retain only the first. Add a second guest in the portal; the personal plan still shows one guest.

**Cause:** Publication stores `result.event` on one local draft and ignores remaining `result.events`. Host refresh only maps existing local plans and omits guest reconciliation. Hosted events absent from local storage are not imported into personal plans.

**Impact:** Calendar omits real outings, guest numbers drift, and a host on another device has an incomplete diary even though the portal still has the events.

**Recommendation:** Create a consistent projection of hosted events by remote ID, include all occurrences and guest/count metadata, and reconcile it without overwriting unrelated local drafts. Clearly distinguish series from individual occurrences.

**Category / suggested command:** Functionality, consistency / `$impeccable harden`.

### [P1] GP-20: Same-event invitation changes do not refresh guest identity

**Location:** `src/App.jsx:857`, `worker/src/index.js:350`, `:364`.

**Reproduction:** Open Emma’s invitation, then navigate in that tab to Sam’s link for the same event, changing only `#invite=…`. The page keeps Emma’s old loaded event/response state. A full reload exchanges the new token and loads current details.

**Impact:** Shared-device guests can see the wrong response context. Source inspection also shows one site-wide guest-session cookie and no explicit invitation identity attached to RSVP submissions, so a second guest link in another tab can change the identity used by an older tab. This cross-tab variant needs a dedicated regression, not a claim that it passed.

**Recommendation:** React to incoming invitation URL changes and browser navigation, return/display the current invitee identity, and bind each response to the invitation context validated by the server. Reject stale/mismatched contexts; retain HttpOnly protection rather than exposing session credentials.

**Category / suggested command:** Identity, functionality / `$impeccable harden`.

### [P1] GP-21: Form-specific colours still fail contrast

**Location:** `src/planner.css:1102` and adjacent optional/type-picker styles.

**Measurement:** Computed placeholders are `rgb(138,145,132)` on `rgb(255,250,240)`, **3.12:1** at 13px. Unselected plan-type labels use `rgb(109,120,102)` on the same surface, approximately **4.46:1** at 11px. The global placeholder rule is overridden by the more-specific `.gp-form` rule.

**Impact / standard:** Helpful prompts and unselected options are harder to read. WCAG 1.4.3 requires 4.5:1 for this small text. Previous primary-button contrast checks did not cover these controls.

**Recommendation:** Remove legacy overrides and use accessible tokens in all form contexts; verify placeholders, optional labels, inactive options and disabled states separately. Do not round 4.46 up to a pass.

**Category / suggested command:** Accessibility, theming / `$impeccable colorize` then `$impeccable audit`.

### [P2] GP-22: Casual outings expose a full hosting form

**Location:** `src/App.jsx:241`–`:565`.

**Evidence:** A friend catch-up exposes guest limit, recurring series, plus-one, public guest-name visibility, email reminders and guest-email controls before saving. On the desktop screenshot the save action is below a scrollable dialog. The three plan kinds largely change labels, not task complexity.

**Impact:** Users planning coffee with one friend must interpret event-management settings before completing a simple plan. Mobile makes the scrolling and decision load greater.

**Recommendation:** Start with name/activity, people, optional date/time and place. Put hosting/email/capacity/series options behind an explicit expandable step. Use distinct primary actions for Save plan, Share details and Publish RSVP invitation, retaining existing functionality.

**Category / suggested command:** UX, information architecture / `$impeccable distill`.

### [P2] GP-23: Guest names are fragile identifiers

**Location:** `src/App.jsx:362`, `:508`, `:1051`, `:1084`; friend editing at `:1910`.

**Reproduction:** Enter `audit emma renamed, Audit Emma Renamed, ` and save. Two guests remain. Case-sensitive Set deduplication removes exact duplicates and blanks, but not equivalent names. Saved people use IDs; guest selection and email lookup use name strings.

**Impact:** The same friend can receive duplicate entries, and renamed friends can lose the connection to existing drafts or name-keyed email fields. Published invitations should preserve their historical names intentionally rather than being silently rewritten.

**Recommendation:** Use stable person/guest IDs for draft selection and email association; normalise typed guest names for duplicate validation while preserving display spelling. Define how renaming affects unpublished drafts versus published records.

**Category / suggested command:** Functionality, form validation / `$impeccable harden`.

### [P2] GP-24: Guest response feedback becomes stale or contradictory

**Location:** `src/App.jsx:592`, `:678`–`:703` and invitation load at `:857`.

**Evidence:** RSVP updates only the response status, not the event/confirmed guest list. Host edits stay invisible in an already-open invitation until reload. A cancelled invitation displays both “No further responses are accepted” and “Your response is saved. You can change it here.”

**Impact:** Guests receive conflicting instructions and may act on old meeting details.

**Recommendation:** Refresh event data after response and on return to an invitation; provide explicit current RSVP/party-size text. On cancellation retain the saved response as history but suppress the invitation to change it.

**Category / suggested command:** UX, state reliability / `$impeccable harden` and `$impeccable clarify`.

### [P2] GP-25: Overnight and multi-day plans have no end date

**Location:** `src/App.jsx:316`–`:344`, `:1087`, `src/lib/plans.js:16` and `:28`.

**Evidence:** Form has one date and two times. Validation rejects an end time before the start; publication and calendar export both construct end timestamp on the start date. The product advertises weekends away, retreats and sleepovers.

**Impact:** These advertised activities cannot be represented accurately through the personal creation flow, even though the backend can store separate start/end timestamps.

**Recommendation:** Add an optional end date for overnight/multi-day activities; preserve start/end instants through editing, discovery import, invitation and calendar export. Include a DST-crossing overnight regression.

**Category / suggested command:** Functionality / `$impeccable harden`.

### [P2] GP-26: Event context is missing from URLs

**Location:** `src/lib/planningModel.js:2`, `src/App.jsx:811`, `:852`, `src/components/HostPortal.jsx:19`.

**Evidence:** Section routing survives refresh, but selected host event, active plan and newsletter edition exist only in component state. The host portal URL remains `?view=host` while managing an occurrence. The popstate handler clears the form but not the active plan ID.

**Impact:** Refresh loses the selected management screen; users cannot bookmark it, and browser Back can change the underlying section while leaving a plan dialog open.

**Recommendation:** Add stable IDs to routes for hosted event/occurrence and plan detail; implement deliberate Back/close behaviour. Keep private invitation tokens out of ordinary dashboard URLs.

**Category / suggested command:** Navigation / `$impeccable harden`.

### [P2] GP-27: List totals and active filters do not reflect the task

**Location:** `src/App.jsx:1122`, `:1474`, `:983`.

**Reproduction:** With two upcoming plans and one undated draft, Still planning displays one card under “Your plans 2”. Importing a dated discovery event while Still planning is selected keeps that filter, so the saved event is hidden once its detail closes.

**Impact:** Counts appear wrong and newly saved plans seem missing.

**Recommendation:** Count the displayed/filter-relevant collection and explicitly set a suitable filter after saving/importing a dated or undated plan. Distinguish Upcoming counts from total plans.

**Category / suggested command:** UX, consistency / `$impeccable clarify` and `$impeccable harden`.

### [P2] GP-28: Host loading briefly announces a false empty state

**Location:** `src/components/HostPortal.jsx:26`, `:35`, `:141`.

**Reproduction:** Navigate to the portal with existing events. Before the list request finishes, the screen says “No hosted events yet. Publish a saved plan to see it here.”

**Impact:** A host gets a misleading statement about their saved data; slow networks amplify it. Refresh also lacks a separate request-pending state.

**Recommendation:** Track loading independently from mutation busy state, render a stable loading placeholder, show empty only after a successful empty response, and distinguish load failure from empty.

**Category / suggested command:** UX, reliability / `$impeccable harden`.

### [P2] GP-29: Discovery status copy promises an unconfigured background run

**Location:** `src/components/NewsletterStudio.jsx:37`, `:169`.

**Evidence:** The same local screen says automatic collection needs its API key, “The background finder checks Dublin every day” and “The next background check runs today.” Live public discovery is empty.

**Impact:** The organiser can assume discovery is active and wait for events that will not arrive.

**Recommendation:** Generate status copy from actual configuration and latest scheduled-job state. Offer manual addition as the active path when disconnected; do not promise a scheduled run without evidence.

**Category / suggested command:** UX, honest status / `$impeccable clarify`.

### [P2] GP-30: Selected page and RSVP choice lack explicit state semantics

**Location:** `src/App.jsx:1294`, `:678`–`:696`.

**Evidence:** Dashboard current-page buttons are styled with a class but have no `aria-current`/equivalent state. RSVP selection changes styling/check decoration and a generic saved message without an explicit programmatic selected value. Friend selection and plan filters already use `aria-pressed` correctly.

**Impact:** Assistive-technology users have less reliable current-location/response context than sighted users.

**Recommendation:** Use normal section links with current-page semantics; represent RSVP choice with suitable pressed/radio semantics or explicit current-response text. Preserve keyboard operation and loading/disabled feedback.

**Category / suggested command:** Accessibility, navigation / `$impeccable harden`.

## Patterns and strengths

The main systemic issues are split local/hosted representations, component-only navigation state, and legacy CSS overriding newer shared tokens. Fixing these seams will remove more friction than adding new homepage sections.

Maintain the working local-first boundary, explicit sync choice, native dialog focus handling, accurate no-booking copy, per-guest invitations, serialized capacity enforcement, recurrence across DST, email acceptance-versus-delivery distinction and newsletter double opt-in. Keep the original artwork/colour personality while simplifying task controls.

## Recommended sequence

1. `$impeccable harden`: GP-18–GP-20, with UI regressions covering post-publish navigation, all series dates and shared-device invitation identity.
2. `$impeccable colorize` / `$impeccable audit`: GP-21 across all form surfaces, not only primary buttons.
3. `$impeccable distill`: GP-22, preserving hosting capabilities behind clear disclosure.
4. `$impeccable harden` / `$impeccable clarify`: remaining P2 state, identity, navigation, feedback and configuration issues. Scope GP-25 explicitly if multi-day plans are deferred from the pilot.
5. `$impeccable polish`: complete phone/tablet/zoom and keyboard review, then deploy and run REL-01–REL-08 against the actual live build.
